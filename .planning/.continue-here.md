# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each was discovered through actual failure in this session.
> Acknowledge each one explicitly before proceeding.

- [ ] CONSTRAINT: local-rehearsal-cannot-validate-a-workflow-file — A GitHub Actions workflow can be rehearsed successfully against the live source and still be rejected outright by GitHub, because the error is in *workflow validation*, not in anything the scripts do. `${{ runner.* }}` is invalid in a workflow-level **and** a job-level `env:` block; GitHub rejects the whole file, and the run appears as a `startup_failure` with **zero jobs**, named by file path instead of by the workflow's own name — which reads as "the nightly is broken" rather than "this one line is wrong". The structural mitigation is to run `gh workflow run <file> --ref <branch>` after ANY workflow edit and read the dispatch result: a rejected dispatch names the exact line and token. The first fix for this was also wrong, and only the dispatch revealed it.
- [ ] CONSTRAINT: green-offline-suite-proves-nothing-about-live — `vitest.config.ts` excludes `**/*.live.test.ts`, so a green `pnpm test` never executes the live suite. The structural mitigation is to run `pnpm vitest run --config vitest.live.config.ts`, or dispatch `nightly.yml` and read its **conclusion**, before claiming a source-touching change is verified. Read the job logs, not just the conclusion.
- [ ] CONSTRAINT: two-document-lockfile-is-correct — `pnpm-lock.yaml` legitimately contains two YAML documents; document one is pnpm 12's `packageManagerDependencies` self-pin. An executor already "repaired" this once and broke fresh installs. The structural mitigation is `pnpm install --frozen-lockfile` before AND after any change that could touch it. **This was violated again in this session** — the orchestrator ran `pnpm add -D -w js-yaml` merely to parse a YAML file, mutating `package.json` and the lockfile. Reverted and proven clean, but the correct move was never to install anything.

**Do not proceed until all boxes are checked.**

|---------|-------------|----------|---------------------|
| local-rehearsal-cannot-validate-a-workflow-file | `nightly.yml` was rehearsed against the live Publications Office successfully, then rejected by GitHub on push: `Unrecognized named-value: 'runner'`. Zero jobs, run named by path. The first fix (move to job-level `env:`) was equally invalid. | blocking | `gh workflow run <file> --ref <branch>` after every workflow edit. A rejected dispatch names the line and token; a successful one proves the file parses. Never infer workflow validity from a local run. |
| green-offline-suite-proves-nothing-about-live | The default vitest profile excludes `*.live.test.ts`. A live test kept a stale corpus key through a 257-passing local suite and failed only in nightly CI, twice. | blocking | Run the live profile explicitly, or dispatch `nightly.yml` and read the conclusion AND the job logs, before calling a source-touching change verified. |
| two-document-lockfile-is-correct | An executor read the lockfile's two YAML documents as corruption and rewrote it as one, dropping pnpm's self-pin; `--frozen-lockfile` then failed outright. The orchestrator later violated the same rule by installing a package to parse YAML. | blocking | Treat the two-document structure as correct. Never install a dependency for a one-off diagnostic — use a throwaway script or a different tool. Prove any lockfile change with `--frozen-lockfile` before and after. |
| identifying-context-reused-as-published-content | The maintainer's personal email, supplied as user-identifying context for authorship, was written into `REPORTING-LEGAL-ERRORS.md` as a world-readable support channel. | a-history-rewrite-does-not-clean-refs-pull | After a successful branch rewrite, `refs/pull/1..5/head` still resolved to the contaminated commit. | verifying-the-fix-instead-of-the-intention | Both of the worst findings in this session were caught by re-running a check AFTER a fix, not by the original check.
